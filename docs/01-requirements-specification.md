# 合租 AA 账单结算器需求规格

## 1. 项目目标与使用者

项目用于记录多人聚餐、旅行或合租消费，根据每笔消费的付款人与参与人计算每个人的应收应付，并生成清晰、可执行的结算建议。

首版面向一名账本组织者。组织者在本地应用中统一维护账本、成员和消费，不要求其他成员注册或登录。

完整业务主链路为：

```text
创建账本 → 添加成员 → 录入消费 → 自动平均分摊
→ 汇总个人余额 → 生成转账建议 → 修改消费后自动重新计算
```

## 2. 首版功能

| 模块 | 首版能力 |
| --- | --- |
| 账本 | 查看多个独立账本；创建账本；修改账本名称；删除账本 |
| 成员 | 查看账本成员；新增成员；修改成员姓名；删除未被消费引用的成员 |
| 消费 | 查看消费明细；记录名称、人民币金额、消费日期、付款人和参与人；修改或删除消费 |
| 分摊 | 将一笔消费的金额在选中的参与人之间平均分摊 |
| 结算 | 展示每人的实付金额、应承担金额和净余额；生成谁向谁转账及转账金额的建议 |
| 数据反馈 | 数据变化后自动显示最新结算；错误输入给出普通用户能够理解的提示 |
| 数据保存 | 数据保存在本机，应用重新启动后仍可恢复已录入内容 |

## 3. 业务规则

### 3.1 账本与成员

1. 不同聚餐、旅行或合租周期可以分别建立独立账本。
2. 同一账本内的成员姓名不得重复。
3. 已经被任一消费引用的成员不得直接删除；组织者需先修改或删除相关消费。
4. 删除账本前必须二次确认；确认删除后，该账本内的成员和消费随账本一并删除。

### 3.2 消费与分摊

1. 消费名称和金额必填；金额必须大于 0，最多保留两位小数，币种固定为人民币。
2. 每笔消费只能选择一名付款人，并且至少选择一名参与人。
3. 付款人可以不属于该笔消费的参与人，以支持纯代付场景。
4. 一笔消费允许只有一名参与人。
5. 参与人的应承担金额按人数平均计算。
6. 金额不能平均整除到分时，多出的分按稳定的成员顺序依次分配。例如 10 元由 3 人承担时，结果为 3.34 元、3.33 元和 3.33 元，且同一组数据每次计算结果一致。

### 3.3 余额与结算

1. 成员净余额等于实付金额减去应承担金额。
2. 净余额为正表示该成员应收，为负表示该成员应付；所有成员净余额之和必须为 0。
3. 转账建议必须能够将所有成员的余额结清到分，并尽量减少不必要的转账，但不承诺数学意义上的全局最少转账次数。
4. 结算结果由当前账本的消费自动推导，不提供手动“重新计算”操作，也不保存实际支付状态。

## 4. 首版不做

- 账号注册、登录、权限控制或多人在线协作。
- 自定义金额、比例、份数等复杂分摊方式。
- 一笔消费由多人共同付款。
- 多币种、汇率或跨币种结算。
- 转账完成标记、实际还款记录或结算历史。
- 图片票据、消费分类、统计图表或预算管理。
- 数据导入、导出或第三方支付集成。
- 移动端应用。
- 微服务、容器化部署、监控平台、压力测试或生产级性能优化。

## 5. 完成标准

- [ ] 能从浏览器完整走通“创建账本 → 添加至少 3 名成员 → 录入多笔消费 → 查看结算”的真实前后端链路，不依赖 Mock 或静态演示数据。
- [ ] 不同消费可以由不同成员付款，并可以选择不同的参与人组合。
- [ ] 修改或删除消费后，个人汇总和转账建议正确更新。
- [ ] 金额计算精确到分，分摊总额等于原始消费金额，全部成员净余额之和为 0。
- [ ] 非正金额、未选付款人、未选参与人、同名成员和删除已被引用成员等操作会被拒绝，并显示明确原因。
- [ ] 关闭并重新启动应用后，已经录入的账本、成员和消费仍然存在。
- [ ] 前端和后端能够完成各自构建；核心结算规则通过少量针对性测试；真实浏览器成功场景和最相关失败场景通过。
- [ ] 本地运行不依赖复杂基础设施，普通低性能轻薄本可以顺畅完成开发与验收。

## 6. 关键验收场景

1. 创建“周末聚餐”账本，并添加甲、乙、丙三名成员。
2. 录入第一笔消费：甲支付 100 元，甲、乙、丙共同参与。
3. 录入第二笔消费：乙支付 40 元，仅乙、丙参与。
4. 核对系统展示每人的实付、应承担和净余额，并给出能够完全结清的转账建议。
5. 修改或删除任一消费，核对所有结算结果随之更新。
6. 分别尝试录入 0 元消费、遗漏付款人、遗漏参与人、创建同名成员和删除已被引用成员，核对系统拒绝操作并解释原因。
7. 重新启动应用，核对“周末聚餐”及其成员、消费仍可访问。
